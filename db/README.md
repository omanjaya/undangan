# Persistence and identity in this first working version

Run `npm run db:migrate` then `npm run db:seed` with `DATABASE_URL` set. Both commands preserve existing data. Seed creates the Amara & Raka invitation; it does not reset drafts or responses.

Storage is split into two JSONB document kinds. `app_global` (one row) holds users, sessions, workspaces with their plan, the global slug index (including old aliases), the media index, and empty `orders`/`packages`/`siteSettings` for billing and admin. `workspace_state` (one row per workspace) holds that customer's invitations, revisions, RSVPs, wishes, guests, budget and media library. Every mutation locks its row (`SELECT ... FOR UPDATE`) and commits atomically. Lock order: never nest; operations touching both documents run as separate steps (if nesting is ever needed: global first, then workspace). The legacy `app_state` table is no longer read at runtime; it is kept untouched as a backup of the pre-multi-tenant data. Splitting workspaces and responses into indexed relational tables is the next scaling step.

Without `DATABASE_URL`, nonproduction uses `DATA_DIR/global.json` and `DATA_DIR/workspaces/<id>.json`, written via atomic rename and an in-process per-file queue. Use one process only in this mode. Production refuses this fallback. The files include guest information and session hashes; keep them private and out of source control.

Accounts live in the global document. Passwords use scrypt with a per-user salt, compared with `timingSafeEqual` (a dummy comparison runs for unknown emails). Sessions are 256-bit opaque tokens stored as SHA-256 hashes, valid 7 days from login, revoked on logout and password change; at most 10 active sessions per user. `OWNER_EMAIL`/`OWNER_PASSWORD` only bootstrap the first admin when no user exists. `npm run db:migrate` applies the SQL files and then migrates legacy single-owner data (`app_state` becomes workspace `workspace-demo` owned by that admin) idempotently inside one transaction guarded by an advisory lock; without owner credentials the data step is skipped and the app performs it on first start. Password reset, email verification and MFA are not implemented.

Mutations require a matching Origin; set `APP_URL` to the public URL behind a reverse proxy. Production cookies use Secure, HttpOnly and SameSite=Lax. Rate limits are in-process per client address; configure proxy address trust carefully and use ingress/shared limiting for multiple replicas.

Public RSVP is deliberately open in this version. A random browser cookie identifies repeat submissions so they update the same response. It does not verify guest identity, does not synchronize across devices, and can be reset by clearing cookies. Each response is limited to five attendees. Wishes remain private until an owner approves them. Invitations are public after publishing; preview requires an owner session and matching workspace. Guest token authorization and private invitations from the plan remain future work.

The application exports only approved wishes publicly. User text must remain rendered as text by the presentation layer. Owner uploads are signature-validated, images are decoded and converted to WebP with metadata removed, and all filenames are server-generated. Anonymous media reads require a current published reference; private drafts and unreferenced assets are not public. Uploads use persistent local storage with a configurable quota. Video and audio are not transcoded. Credential rotation invalidates existing sessions.

Daftar tamu (tamu, kode pribadi, status kirim/buka/check-in, templat pesan WhatsApp) disimpan di payload yang sama pada kunci `guests` dan `guestTemplates`; migrasi `0002_guests.sql` hanya memastikan kunci itu ada. `npm run db:migrate` kini menjalankan semua berkas di `db/migrations` berurutan (semuanya idempoten).
